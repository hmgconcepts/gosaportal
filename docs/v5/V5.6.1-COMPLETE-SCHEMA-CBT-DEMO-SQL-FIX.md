# School Connect V5.6.1 — Complete Schema, Multi-Subject CBT and Demo SQL Repair

## 1. One complete production schema

`database/complete-schema.sql` is now the only production SQL installer. It is
self-contained for new projects and cumulative upgrades, and includes every table,
compatibility column, repair, constraint, index, trigger, view, RLS policy, grant
and RPC required by V5.1–V5.6.1.

The schema was cleaned so each `public` function has one authoritative definition.
A final self-sufficiency block checks critical tables and RPC signatures and raises
a clear installation error if anything is missing. The last successful result is:

```text
School Connect V5.6.1 complete cumulative schema installed successfully ✅ — no other production SQL is required
```

Automated PostgreSQL-compatible execution runs the complete schema twice against
the same database. Both runs must succeed. Newly generated client ZIPs contain only
`complete-schema.sql` as production SQL.

The versioned/focused SQL files retained in source are historical narrow upgrade
references. Do not run them after the complete schema.

## 2. Multi-subject/open CBT service repair

### Symptom

```text
Exam service unavailable
record "s" is not assigned yet
```

### Cause

`cbt_get_public_exam_v6` declared an untyped PL/pgSQL `record` for a possible
student. For an open examination with no admission number, no student query ran,
but the function still evaluated `s.id`. Open multi-subject papers therefore
failed before the candidate could start.

### Repair

- Uses typed `%rowtype` variables.
- Initializes the optional candidate as JSON `null`.
- Never reads student fields unless a lookup actually succeeded.
- Open and multi-subject papers work without an admission number.
- If an optional admission number matches, official identity is still returned.
- Registered papers still require and enforce the official active student/roster.
- `cbt_submit_v6` received the same typed and qualified identity hardening.

The executed regression test calls V6 with an open multi-subject paper, a blank
admission number and two subject questions. It must return `ok=true`, two questions
and `candidate=null`—not a server exception.

## 3. Demo `exam_id` ambiguity repair

### Symptom

```text
ERROR: 42702: column reference "exam_id" is ambiguous
```

### Cause

The specialised demo block used a PL/pgSQL variable named `exam_id` while inserting
into/querying tables that also had an `exam_id` column.

### Repair

- Renamed the variable to `v_exam_id`.
- Qualified student/result aliases (`st`, `cr`).
- Uses `select v_exam_id, ...` for roster rows.
- Uses `where cr.exam_id=v_exam_id` for admission letters.
- Uses conflict-safe roster insertion without an ambiguous conflict target.

The complete execution test now runs `demo-users.sql`, then `demo-seed.sql` twice.
Both seed runs succeed and retain roster/admission-letter sample data.

## Deployment

1. Back up Supabase.
2. Run the entire updated `database/complete-schema.sql`.
3. Do not run any focused/versioned SQL afterward.
4. For the separate demo project only, create the five Authentication users, run
   `demo-users.sql`, then run `demo-seed.sql`.
5. Deploy every updated frontend file.
6. Close existing tabs and hard-refresh to replace the old PWA cache.
7. Test one open multi-subject code with no admission number and one registered
   exam with an official admission number.

Frontend deployment without the updated complete schema cannot replace the broken
server RPC and is therefore insufficient.
